# 캘린더 (B1)

> 기획: [B1 정부상품 캘린더](../planning/b1-government-calendar.md)

정책 저축상품과 청년 금융 지원 정책의 신청 일정을 한 목록으로 보여준다. 응답의 `tier`로 기획의 두 계층을 구분한다.

| `tier` | 기획 | 데이터 | 상세 이동 |
| --- | --- | --- | --- |
| `POLICY_PRODUCT` | 1계층: Y-Fin 정책상품(POLICY001~016) | `policy_product_round` | Y4 상세(`productId`) |
| `YOUTH_POLICY` | 2계층: 온통청년 청년 금융 지원 정책 | `youth_policy`, `youth_policy_round` | 온통청년(`externalUrl`) |

## 1계층 데이터

정부상품은 수집기 `manual-products.json`으로 수동 입력하는 상품이고, 온통청년과 연결할 키가 없다. 온통청년은 같은 사업이라도 연도·회차마다 정책번호를 새로 발급하고, 공고보다 늦게 올리거나 아예 올리지 않는 경우가 많다(2026년 16종 중 신청 시작 전에 올라온 것은 4종). 그래서 기획대로 사람이 확인한 회차만 둔다.

- 수집기 `manual-product-rounds.json`에 상품 코드별 회차(시작일, 종료일, 근거 링크)를 적고, 수집기가 `policy_product_round`에 맞춘다. 파일에서 빠진 회차는 지우고, 날짜가 바뀐 회차는 `schedule_changed_at`을 남긴다.
- 지난 회차도 지우지 않는다. 다음 해 모집 시기를 가늠하는 근거가 된다.
- 가입 가능한 옵션이 하나도 없는 상품(수집에서 사라져 비활성화된 상품)의 회차는 보여주지 않는다.
- 나이는 옵션(일반형·우대형 등)마다 다르면 가장 넓은 범위를 쓴다. 지역은 옵션 키워드 `REGION_*`이고, 없으면 전국이다.
- 기관은 첫 번째 가입 가능 옵션의 제공기관, 설명은 상품 요약(`content_summary`)이다.

## 2계층 데이터

수집기(Fin-API)가 온통청년 `getPlcy` API에서 정책을 받아 `youth_policy`, `youth_policy_round`(V10)에 쓴다. 추천 대상인 `product`와는 테이블을 나눴다.

| 항목 | 규칙 |
| --- | --- |
| 범위 | 기획의 "자산형성 저축·공제·신용회복". 온통청년 분류와 관계없이 정책 이름 키워드로 고르고, 주거 정책과 세금 공제는 뺀다. 수집기 `YouthPolicyParser.SCOPE_NAME`, `EXCLUDED_NAME`. 2026-11 기준 3,843건 중 90건 |
| 신청기간 구분 | `aplyPrdSeCd` 0057001 특정기간 → `PERIOD`, 0057002 상시 → `ALWAYS`, 0057003 마감 → `CLOSED`(표시 안 함) |
| 회차 | `aplyYmd`의 `yyyyMMdd ~ yyyyMMdd` 하나가 한 회차. 여러 회차는 문자 그대로의 `\N`으로 이어져 온다. 읽을 수 없는 회차는 버린다 |
| 일정 변경 | 같은 순번(`round_no`) 회차의 날짜가 바뀌면 `schedule_changed_at`을 남기고, API는 7일간 `scheduleChanged = true` |
| 사라진 정책 | 이번 수집 목록에 없으면 `is_active = false` |
| 나이 | 온통청년은 제한 없음을 0으로 준다. 0은 `NULL`로 저장 |
| 지역 | `zipCd`(시군구 5자리 코드) 원문을 `region_codes`에 저장. 비어 있으면 지역 제한 없음 |

온통청년 분류로 먼저 거르지 않는 이유: 내일채움공제 계열은 `재직자`, 학자금 신용회복은 `교육비지원` 분류에 있고, `취약계층 및 금융지원` 분류는 출산지원금·돌봄처럼 금융과 먼 정책이 70% 넘게 섞여 있다.

## API

두 엔드포인트 모두 비로그인으로 쓸 수 있다. 신청 기간 유형, 상품 분류, 내 조건 맞춤 필터는 FE가 응답 필드(`type`, `tier`, `eligibility`)로 거른다. 필터 칩마다 건수를 보여줘야 해서 서버가 거르지 않는다.

| API | 내용 |
| --- | --- |
| `GET /calendar/events?from=yyyy-MM-dd&to=yyyy-MM-dd` | 기간(양 끝 포함)에 찍히는 시작·마감 일정. 날짜순, 같은 날은 마감 먼저, 같은 유형이면 1계층 먼저 |
| `GET /calendar/summary` | 오늘 기준 정보: `openNow`(지금 신청 가능, 마감 가까운 순), `yearRound`(접수 중인 연중 접수), `always`(상시 신청, 2계층만) |

`from`이 `to`보다 늦거나 날짜 형식이 틀리면 400이다. `asOf`는 온통청년 마지막 수집 시각으로, 하단 고지의 데이터 기준일에 쓴다. `roundId`는 계층마다 따로 매겨지므로 `(tier, roundId)`로 구분한다.

## 일정 판정

`CalendarSchedule`이 기획의 판정 규칙을 그대로 옮겼다. 두 계층에 같이 쓴다.

- 연중 접수: 기간이 양 끝 포함 180일 이상이고 12/31에 끝나는 회차. 마감 일정이 없고, 시작일이 미래면 시작 일정만 찍는다.
- 그 외 회차: 시작·마감 일정 두 개. 시작일과 종료일이 같으면 마감 일정만.
- 지금 신청 가능: 오늘이 시작일~종료일 사이(양 끝 포함)인 회차. 연중 접수는 `yearRound`로 따로 준다.

## 자격 판정

`PolicyEligibility`. 나이와 거주지역만 본다. 2계층은 기획과 같고, 1계층은 기획(Y3-2 자격 필터 전체)보다 좁다([기획과 구현 차이](plan-vs-implementation.md)). 약관 동의를 마친 로그인 사용자에게만 판정하고, 그 외에는 `eligibility = null`이다.

- 저장된 추천 입력 프로필(`user_profiles`)의 생년월일과 1단계 거주지역(`REGION_*`)을 쓴다.
- 제한이 있는데 프로필 값이 비면 `NEEDS_INFO`. 다른 조건에서 이미 미충족이면 `INELIGIBLE`이 우선한다.
- 2계층 거주지역은 `zipCd` 앞 두 자리(시도 코드)로 맞춘다. 2026 행정구역 개편으로 광주·전남은 `12`(전남광주통합특별시), 강원은 `51`, 전북은 `52`를 쓴다. 모든 시도가 대상이면 전국으로 보고 `regions`를 비운다.
